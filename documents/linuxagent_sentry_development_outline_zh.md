# LinuxAgent Sentry 开发方案：步骤拆分提案

状态：第一轮拆分，供讨论；不是已批准的实施顺序。本提案以 `linuxagent_sentry_mvp_plan_zh.md` 中已达成一致的行为约定为依据，不修改其功能语义。本轮明确步骤、依赖、交付与评审边界；步骤确定后，再展开每一步的函数级修改、完整数据结构、英文 Prompt 和测试用例。

## 1. 开发目标

### 1.1 任务背景

LinuxAgent 当前通过规划、工具执行和记忆更新推进任务，尚未接入本次约定的故障诊断、恢复验证和修复经验复用机制。相邻 Sentry 项目提供软故障分类、诊断、恢复验证及经验抽象的参考实现。本次在现有 Processor 流水线中渐进接入这些能力。

### 1.2 开发需求

- 程序识别响应／动作合法性硬故障，生成固定建议，允许下一轮纠错和检验；硬故障优先于软故障处理。
- 在工具执行后、记忆更新前执行 SentryEvaluation；检测软故障，注入一次诊断建议，并在五个有效恢复轮次后验证。
- 统一执行后观测与下一轮规划观测，保留紧凑轨迹及恢复验证所需的两张截图。
- 恢复验证成功后执行 FailureSummary，生成可复用经验并写入 JSON playbook；再次发现软故障时按标签检索并一次性注入经验。

### 1.3 开发目标

交付可按配置启停、仅作用于 LinuxAgent 的最小实现。建立“硬故障纠错”和“软故障诊断—恢复—验证—总结—复用”两条可验证链路，保持原有工具执行、普通记忆和结果上报的职责。每一步都有独立可审阅的变更和无真实模型调用的验证证据。

## 2. 开发约束、限制

1. 只在 `UFO3` 的 `sentry_version` 分支开发；保留现有未提交修改。本轮只编写拆分提案，不修改运行代码。
2. 仅接入 LinuxAgent；不重写公共 Processor 执行算法，不改变其他平台和 AIP 结果格式。新增功能开关默认关闭，关闭时保持原路径。
3. 开发过程中允许 mock 测试及临时目录文件测试，禁止真实模型请求，包括初始化探测、备用模型和通过启动程序间接触发的请求。中间步骤用 fake/mock 驱动验证，不运行尚未完成的真实 Agent 链路。
4. **硬故障轮次不进入轨迹、不计软恢复步数；软事件 pending 后保留原计数，硬故障解除再继续。同时只存在一个活动软故障，恢复期间不检测新软故障。**
5. **合法 FINISH 通过硬检查后立即放行，包括软恢复期间及恰好第五步；未经恢复验证的事件不总结、不落盘。** 保留原 FAIL、步数上限和取消语义。
6. 五步以有效规划／执行轮次计数，不以工具调用数量计数。检测无图；验证只有原始触发图和当前图；总结只有文本。
7. Prompt、固定提示、标签定义和示例文本使用英文。一次性干预由共享 Context 调度；不把诊断反复写入普通 memory 或反复注入规划。
8. Playbook 使用一个可配置的 JSON 文件，提供同进程读改写保护；多进程写入分别配置路径。检索不调用模型，不引入向量库或自动动作回放。
9. MVP 只保留必要的 schema 检查和异常边界；不增加复杂重试、熔断、评分器或独立日志系统。附加能力失败不应使主任务 FAIL。
10. 每一步同时交付相关验证，不把测试全部留到最后。Mock 验收证明接口、数据流及调度行为，不据此宣称模型的实际诊断或总结质量已经验证。

## 3. 开发步骤

推荐顺序为步骤 1 至 10。步骤 1—3 建立基础设施及硬故障纠错；步骤 4—6 完成软故障恢复；步骤 7—9 完成经验积累与复用；步骤 10 验收跨步骤行为。依赖用于明确交付先后，不要求并行开发。

各步骤的“交付要求”面向开发结果，“评审要求”面向变更和证据的审查，不代表需要增加运行时拦截机制。

### 步骤 1：配置、任务状态与数据协议

**a. 开发目标：** 为后续模块确定一致的数据边界和功能开关，先保证状态不会跨任务污染。

**b. 覆盖范围：** 无前置依赖。涉及 `config/ufo/agents.yaml`、配置加载／schema、`ufo/module/context.py`、`LinuxBaseSession.reset`，新增 `sentry_schema.py` 的基础协议，以及相关测试 fixture。

**c. 细节：** 增加 SENTRY_AGENT 配置、ENABLED、PROMPT、PLAYBOOK_PATH、PLAYBOOK_TOP_K；模型连接配置继承 APP_AGENT，可覆盖。增加任务内 SENTRY_STATE 字典，明确 task_key、recent_steps、active_soft、active_hard、pending_guidance、latest_observation、last_verification 的默认值和生命周期。定义紧凑 Step、硬故障、软故障检测／验证响应及标签；经验结构在步骤 7 补齐。本步不注册新执行阶段、不构造真实模型客户端。

**d. 交付要求与验证标准：** 配置缺省／覆盖可加载；两个 Context 的可变字典互不共享；reset 清空本任务状态；旧配置仍能使用。准备后续用例共用的 fake 模型入口及观测 fixture，防止测试构造对象时触发模型探测。

**e. 评审要求：** 检查默认关闭是否完整、状态归属是否清楚、是否误修改现有配置值；确认跨轮数据在共享 Context，本轮数据在 local context，模型对象和整个 playbook 不进入任务字典。

### 步骤 2：执行后观测与紧凑轨迹构造

**a. 开发目标：** 建立可靠的观测输入，消除重复采集，为后续检测提供真实执行证据。

**b. 覆盖范围：** 依赖步骤 1。涉及 ProcessingPhase、`LinuxAgentProcessor._setup_strategies`、`LinuxDesktopCollectionStrategy.execute`，新增 `sentry_evaluation_strategy.py` 中的阶段骨架、观测 helper 和轨迹构造函数。

**c. 细节：** 将 SENTRY_EVALUATION 放在 ACTION_EXECUTION 后、MEMORY_UPDATE 前，本步只处理观测和记录构造。首轮无缓存时初始化；每轮执行后更新原图、标注图、控件／UI／窗口信息，下一轮整体复用。构造 step_id、reasoning、action.raw、observation；reasoning 来自显式 thought，observation 来自真实执行结果。按既定长度压缩，不修改原工具结果。本步构造当前记录，窗口准入和恢复计数留给步骤 5—6。

**d. 交付要求与验证标准：** fake 观测调用证明首轮初始化一次、下一轮不重复采集；图片与控件属于同一批观测；新任务不复用旧缓存。构造样本验证失败／未执行结果、工具错误和截断标记得到保留；原始输入不被改写。

**e. 评审要求：** 检查阶段顺序、观测所有权和新旧控件混用风险；确认压缩仅影响 Sentry 副本，没有把规划模型声称的 observation 当成工具事实。

### 步骤 3：硬故障拦截、一次性提示与下一轮纠错

**a. 开发目标：** 先完成不依赖 Sentry LLM 的硬故障纠错链路，使非法响应能够进入下一轮修正。

**b. 覆盖范围：** 依赖步骤 1—2。新增 `sentry_hard_guard.py`；修改 Linux LLM／Action 策略、Linux 专用 MemoryUpdate、LinuxAgent.message_constructor 和 Linux prompter；加入英文硬故障固定模板。

**c. 细节：** 覆盖 invalid_json、invalid_response、invalid_tool_call、invalid_target。分开获取原始响应与解析，保留解析失败详情；已知非法动作跳过执行，返回 CONTINUE 而非 FAIL，清除本轮伪终态结果。parsed_response 缺失时成功跳过普通记忆更新。打通 pending_guidance 的生成、下一轮消费和清空；用相同程序规则检验修正结果。合法 FINISH 放行。与软恢复计数的联动在步骤 6 完成。

**d. 交付要求与验证标准：** 用两轮 fake 规划验证“非法 JSON → 固定提示 → 合法响应继续”；非法工具不会执行，解析失败不进入依赖 parsed_response 的普通记忆路径；仍非法时下一轮继续修正；整个硬故障路径不调用 Sentry LLM。

**e. 评审要求：** 检查是否绕开 FAIL middleware 的错误路径，是否丢失原始响应／成本，是否错误地把普通非零退出码或连接异常归为硬故障；确认提示要求完整 LinuxAgent JSON，且没有当轮内部重规划循环。

### 步骤 4：SentryAgent 检测／验证接口与英文 Prompt

**a. 开发目标：** 建立可单独调用和测试的 Sentry 模型接口，先验证输入输出，不在此步实现恢复调度。

**b. 覆盖范围：** 依赖步骤 1—3。新增 `sentry_agent.py`、`sentry_prompter.py`，扩充 `sentry.yaml`；增加 AgentType.SENTRY、配置查询和 get_completions 路由；在 LinuxAgent 启用时创建轻量 SentryAgent。

**c. 细节：** 实现 async detect 和 verify，复用现有 LLM 层，明确成本返回及响应解析边界。检测输入任务、分类定义和最多五步文本，输出 failure_type／labels／evidence／diagnosis／advice。验证输入原始故障、当前建议、五步文本、分类恢复标准和两张原图，输出 recovery_status／evidence／diagnosis／advice。完整英文模板沿用讨论文档第 5 节；summarize_failure 留给步骤 8。

**d. 交付要求与验证标准：** fake LLM 捕获请求，断言检测无图片、验证恰好两图且顺序正确；正常 JSON 可解析，非法响应／调用异常可由调用方处理，成本可累计。测试覆盖 SENTRY 配置选择，构造 SentryAgent 不产生真实请求。

**e. 评审要求：** 检查是否误用 EvaluationAgent 的完成评估 schema、是否把恢复等同于整体任务完成、是否把硬故障交给模型；确认没有新 AgentFactory 路由或工具执行权限。

### 步骤 5：新软故障检测与诊断注入

**a. 开发目标：** 打通“符合条件的执行轮次 → 诊断 → 下一轮规划收到一次建议”。

**b. 覆盖范围：** 依赖步骤 2—4。扩充 SentryEvaluation 的检测分支、共享状态读写和英文软故障提示；复用步骤 3 的提示传递通道。

**c. 细节：** 先处理硬故障及终态；仅有效继续轮次进入 recent_steps，窗口最多五条。无活动软故障时调用 detect；发现故障才创建 event_id、保存原始类别／标签／证据、trigger_step／触发截图，计数从 0 开始，排队一次建议。此时 retrieved_experiences 为空。已有软故障时不检测新故障；检测失败不创建伪事件，五步验证在下一步接入。

**d. 交付要求与验证标准：** fake 检测返回 no_failure 时无干预；返回软故障时创建唯一事件，下一轮收到 Sentry 身份说明、证据及建议，之后不重复注入。硬故障及合法 FINISH 不调用 detect；触发截图不会随观测缓存更新而丢失。

**e. 评审要求：** 检查调用条件、触发步不计入后续五步、提示消费时机；确认诊断没有写入普通 memory，也没有因检测异常中断主任务。

### 步骤 6：五步恢复验证及硬软故障优先级

**a. 开发目标：** 完成软故障恢复调度，包括暂停、继续、重复观察和结束边界。

**b. 覆盖范围：** 依赖步骤 3—5。扩充 SentryEvaluation、硬故障与 active_soft 的联动、终止清理，以及本轮 verified_recovery 数据交接。

**c. 细节：** 只有后续有效轮次增加 recovery_count，满五轮调用 verify。硬故障使软事件 pending，窗口和计数不变；纠错通过且继续执行后恢复计数。resolved 时深拷贝证据快照至 local context，再清空软事件；unresolved 更新建议并从 0 重计；验证异常或缺图记 unverified，保留原故障重新观察。保留原触发截图。合法 FINISH 即使在第五步也不验证，待验证事件记 incomplete。无本轮成功验证时 verified_recovery 为空。

**d. 交付要求与验证标准：** 验证“恢复两步 → 硬故障 → 修正通过计第三步 → 第五步验证”的调用与状态序列；硬故障反复出现不重置计数。覆盖 resolved、unresolved、unverified 和第五步 FINISH；证明五步窗口不含触发步／硬故障步，成功快照在清空事件后仍完整可用。

**e. 评审要求：** 对照状态迁移逐条检查优先级与计数，不以 session_step 相减代替有效轮次计数；确认没有双事件、恢复期间重复检测、FINISH 拦截或旧结果触发重复验证。

### 步骤 7：Playbook 文件存储与确定性检索模块

**a. 开发目标：** 建立独立可验证的经验存储和查询模块，本步不触发 LLM 总结或线上注入。

**b. 覆盖范围：** 依赖步骤 1；推荐在步骤 6 后交付。新增 `ufo/experience/sentry_playbook.py`、经验／文件结构、`tests/test_sentry_playbook.py`；补充默认运行数据目录的 gitignore。

**c. 细节：** 定义 SentryExperience：failure_type、labels、trigger_pattern、applicability、repair_principle、repair_steps、success_check、evidence；程序补 entry_id／created_at，文件采用 version／entries。实现 append 的同进程路径锁、读改写和原子替换；同 event_id 不重复追加。retrieve 按同类别、标签交集非空筛选，交集数量及追加新旧排序，默认 top 3，无交集不兜底。文件缺失为空库，损坏不覆盖。

**d. 交付要求与验证标准：** 在临时目录验证首次建库、追加／重载、事件去重、并发写入保留记录、写失败不破坏原文件。用固定经验集验证标签筛选、排序和 top_k；读取损坏文件返回空经验并报告异常，不调用 LLM。

**e. 评审要求：** 检查程序元数据与 LLM 内容的边界、文件路径与任务生命周期、原子替换和读改写锁的覆盖范围；确认未接入现有向量 RAG，未保存完整轨迹或截图。

### 步骤 8：FailureSummary 阶段与经验落盘

**a. 开发目标：** 打通“本轮恢复验证成功 → 一次总结 → 经验写入”。

**b. 覆盖范围：** 依赖步骤 4、6、7。新增 FAILURE_SUMMARY 阶段和 `FailureSummaryStrategy`；在 SentryAgent／prompter 中加入 summarize_failure 及英文总结模板；Linux Processor 注册该阶段。

**c. 细节：** 阶段置于 SentryEvaluation 后、MemoryUpdate 前，只消费本轮 verified_recovery。输入原始故障、触发记录、当前建议、检索经验、最后五步和成功验证证据，不传图。Prompt 要求区分建议、执行与事实，抽象适用条件／修复原则／步骤／恢复信号；证据不足返回 null。通过基础 schema 和原标签一致性检查后 append；程序填写元数据，累加总结成本。

**d. 交付要求与验证标准：** fake 总结返回有效经验时只写入一次；后续轮次不因 last_verification 仍为 resolved 而重复总结。硬故障恢复、直接 FINISH、未恢复／未验证不调用总结；null、非法 JSON、标签不一致、模型／写盘错误均不回滚恢复状态或使任务 FAIL。

**e. 评审要求：** 检查快照生成和消费的生命周期、是否误学未经验证的事件。对英文 Prompt 和构造样例做静态内容评审，确认能区分“推荐过”与“实际执行且有证据”；不以 mock 输出宣称模型已经具备抽象能力。

### 步骤 9：新软故障检索经验并注入规划

**a. 开发目标：** 完成跨事件经验复用，保留 Sentry 当前诊断和 LinuxAgent 的动作规划职责。

**b. 覆盖范围：** 依赖步骤 5、7、8。修改 SentryEvaluation 新故障分支、active_soft 的经验快照和软故障提示模板；复用现有 pending_guidance 通道。

**c. 细节：** 新诊断成功后程序检索一次，将结果快照保存在事件内。注入仅包含触发现象、适用条件、修复原则、步骤、恢复判断标准，不包含旧任务证据／存储元数据。英文模板说明经验来自其他事件，须结合当前环境判断适用性，不自动回放历史动作；无匹配／读失败则保留原诊断建议。后续恢复、硬故障解除及未恢复重试不重新检索、不重复附带旧经验。

**d. 交付要求与验证标准：** 用步骤 8 写入的记录驱动后续新事件，证明匹配经验与诊断一起出现在下一轮 Prompt 且只出现一次；不匹配或读失败仍正常注入诊断。检索不增加 LLM 调用，恢复期间没有重复查询或重复经验段。

**e. 评审要求：** 检查查询是否严格发生在新故障触发点、是否把整库或历史命令误当作当前任务指令；确认经验不会覆盖当前故障证据，也不会因命中经验跳过规划或恢复验证。

### 步骤 10：跨轮、跨任务集成验收与交付整理

**a. 开发目标：** 验证各步骤组合后的实际数据流及兼容性，形成可交付实现。

**b. 覆盖范围：** 依赖步骤 1—9。以 fake 模型和 dispatcher 驱动真实 Linux Processor 阶段组合、共享 Context 和任务 reset；整理配置说明、变更清单及测试结果，不增加新的功能模块。

**c. 细节：** 场景一覆盖正常检测、软故障、硬故障插入、五步成功验证、总结落盘。场景二启动新任务并验证状态清空、playbook 保留、新故障检索和一次性注入。另覆盖第五步合法 FINISH、非法响应重试、Sentry／文件异常、功能关闭及其他平台不注册新阶段。沿用已有单元测试，不重复建设测试框架。

**d. 交付要求与验证标准：** 提交实际运行命令及结果、关键调用顺序／次数断言、文件列表。阶段顺序、成本累加、截图复用、普通记忆和原结果上报均符合约定；所有模型入口含初始化探测均被替换，未发出真实模型请求。已有相关测试通过，失败项给出明确原因和处理结果。

**e. 评审要求：** 根据最终 diff 与测试证据检查需求是否遗漏、公共流程是否被扩大修改、是否引入未约定依赖或持久数据；区分已验证的调度行为与尚未真实评测的模型效果。核对开发分支及用户原有修改未被覆盖。

## 本轮讨论范围

本轮先确定上述 10 步的粒度、先后依赖和验收边界。正式方案沿用“开发目标—开发约束／限制—开发步骤”三部分结构；每步展开 a—e，给出确切文件／类／函数、字段类型与默认值、适用的完整英文 Prompt、关键执行伪代码、具体测试输入与预期输出、评审检查项。原讨论文档作为行为依据保留，正式方案不再仅按架构模块罗列文件。
